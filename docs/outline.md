2. 背景・目的 (01:00 - 06:00; 5min)
   1. Foundry Agent Serviceとは (1min)
      - エージェントを作成・管理できるプラットフォーム
      - Azureの認証・監視・リソース管理と統合しやすい
      - GUIで作成・編集できるだけでなく、**API経由でも操作できる** (←重要)
   2. GUI上でツール開発する際の困りごと (Difyでの経験をもとに) (2min)
      - **変更管理が難しい**
        - 本番運用を続けながら、バグ修正や機能追加といった変更を加えられるようにするには、本番環境と分離した環境 (開発環境) が必要
        - Webアプリケーションのスクラッチ開発では一般的だが、GUIツールだと難しくなりがち
          - Difyの場合には以下のようにしていた
            - 稼働している本番用のアプリをコピーする
            - 変更を加えて動作確認
            - 本番用のアプリに同じ変更を加える (**手動デプロイ**)
          - チーム開発するとさらに難しい
            - 開発者全員が本番用のアプリを触るのは危険
            - 別のパターンとして、開発者が本番用のアプリのクローンを個々に作成し、変更後に、本番用のアプリに反映するといった運用方法があるが、競合の解消やxxxといった問題が発生する
      - 手動操作が多い
        - 手動操作による開発プロセスが前提のため、コーディングエージェントをはじめとした生成AIの恩恵を受けられない
        - 本番環境への反映は手動にならざるを得ない
   3. そこで、GitOpsですよ (2min)
      - アプリ開発ではGitFlowやGitHub Flowなどが使われてる
      - **システムの設定や構成をGitに置き、Gitの変更を起点にデプロイ・運用**する考え方 (https://about.gitlab.com/topics/gitops/)
        - アプリケーション開発の現場で使われているGitに基づいたフレームワークを、アプリケーションだけでなく、インフラまで含んだシステム全体に対しても適用することで、運用を効率化しようという考え方
      - 以下のような利点がある:
        - **変更管理の効率化**
          - 変更履歴の追跡
          - ロールバックしやすい
          - Pull Requestでレビュー可能 (ゲート設定可能)
          - GitFlowやGitHub Flowといったブランチ戦略に基づいてチーム開発可能
        - 自動化
          - エージェントによる開発/レビュー (GitHub Copilotとのシナジー)
          - デプロイ自動化
      - **GitOpsを実現するには、運用対象のシステムが「定義できる」「反映できる」こと**が必要
        - 定義できる = 望ましい状態をGit上のファイルで表現できる
        - 反映できる = その定義を対象環境へ自動適用できる
   4. なぜ、Agent Service × GitOpsなのか? (30s)
      - Azureでは、API経由でリソースの作成・更新・取得ができる
      - Agent Serviceでも、APIを使ってエージェントや関連リソースを操作できる
      - さらに、API経由でエージェントの設定情報を取得し、Gitで管理できる定義として扱える
        - いわば "Agent as Code"
      - つまり、Agent Serviceは「定義できる」「反映できる」という要件を満たしているため、GitOpsに乗せることが可能
   5. このセクションのまとめ (30s)
      - GUIベースのAIツールは素早く開発できる一方で、変更管理・チーム開発・本番反映の統制が難しくなりやすい
      - Agent ServiceはAPI経由でエージェントの設定取得・反映ができるため、エージェントをGitOpsに乗せることが可能
      - これにより、エージェントの変更をGitHub上でレビューし、承認された定義だけを環境へ反映する運用を実現できる
