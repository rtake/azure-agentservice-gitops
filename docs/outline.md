2. 背景・目的 (01:00 - 06:00; 5min)
   1. Foundry Agent Serviceとは (1min)
      - エージェントを作成・管理できるプラットフォーム
      - GUIで作成・編集できるだけでなく、**API経由でも操作できる**
   2. GUI上でツール開発する際の困りごと (Difyでの経験をもとに) (2min)
      1. 開発環境と本番環境の分離・同期が難しい
         - 本番運用では、稼働中の本番環境を直接変更するのではなく、開発環境で変更・検証してから本番へ反映したい
         - GUI型ツールでは、開発環境と本番環境の差分管理や同期が難しくなりやすい
         - Difyでも、本番アプリをコピーして検証し、同じ変更を本番へ手動反映するような運用になりがちだった
      2. 変更管理・統制が難しい
         - 変更差分が見えにくい
         - Pull Requestのようなレビュー・承認プロセスに乗せにくい
         - 変更履歴の追跡やロールバックがしづらい
      3. チーム開発が難しい
         - 複数人が同じGUI上で変更すると、上書き・競合・反映漏れが起きやすい
   3. そこで、GitOpsですよ (2min)
      - アプリケーション開発では、Git/GitHubで変更管理している
      - それと同じように、**システムの設定や構成をGitに置き、Gitの変更を起点にデプロイ・運用**する考え方をGitOpsという
        - https://about.gitlab.com/topics/gitops/
      - 以下のような利点が得られる
        1. 環境間の反映を自動化・再現可能にできる
           - 開発環境で検証した定義を、本番環境へ自動反映できる
           - 手動反映による作業ミス・反映漏れ・環境差分を減らせる
        2. 変更管理・統制がしやすい
           - Pull Requestでレビュー・承認できる
           - 変更履歴の追跡
           - ロールバックしやすい
        3. チーム開発を効率化できる
           - アプリケーション開発のベストプラクティス (xxx等) が活用できる
   4. なぜ、Agent Service × GitOpsなのか? (30s)
      - GitOpsを実現するには、運用対象のシステムが**ファイルで定義できる**ことと、**対象の環境へ自動で反映できる**ことが必要
      - Agent Serviceでは、API経由でエージェントの設定情報を取得できる
        - いわば "Agent as Code"
      - また、API経由でエージェント定義を対象プロジェクトへ反映できる
      - このように、Agent Serviceは「定義できる」「反映できる」という要件を満たすため、GitOpsに乗せることができる
3. 成果物の概要 (06:00 - 08:00; 2min)
   1. 全体アーキテクチャ
      - Agent Serviceのプロジェクトを開発用と本番用に分ける
        - 開発者は、開発用プロジェクトでエージェントを編集する
      - GitHub上のリポジトリでエージェントの設定をバージョン管理する
      - Pull Requestを、本番反映前のレビュー・承認ゲートにする
      - GitHub Actionsが、承認済みのエージェント定義を本番用プロジェクトへ反映する
   2. 処理フロー概要
      - 開発者がエージェントを更新する
      - システムが更新後のエージェント設定を取得しGitHubにアップロードする
      - システムがPull Requestを作成する
      - 管理者がPull Requestをレビューし、問題なければマージする
      - GitHub Actionsが、マージされたエージェント設定を本番用プロジェクトに反映する
4. デモ (08:00 - 13:00)

5. アーキテクチャ詳細 (13:00 - 17:00; 4min)

   - Azure Functionsがエージェント設定をAPIで取得しGitHubにアップロードしてPull Requestを作成する
     - Azure Functionsは責務ごとに分離しQueueを使って疎結合にしている
